# GS-куллинг треугольников DOOM: почему пропадают треугольники и что сделано (28.10)

## Шейдеры
Шесть geometry shader'ов, одна и та же программа (отличаются только `Location` varying'ов):
`703f1fcc3cda7204`, `351c0bfc62457935`, `78c87a041d7f7005`, `919c10a8430cedb8`, `ee0022fdb45318d5`, `ef97a2735bfdeae6`
(`work/shaders-vk/*.xgs`, SPIR-V с offset 192; Triangles -> TriangleStrip, 3 вершины, Invocations 1).

Что делает каждая инвокация (один треугольник):
1. `c16[0].y != 1` -> просто эмитит треугольник (куллинг выключен).
2. Тесты, результат `vis` (1 = видим):
   - frustum: AND out-code'ов вершин (varying loc2.x) != 0, гейт `c16[0].z != 0`;
   - бит 64 в OR out-code'ов (вершина за near) -> сразу видим, остальные тесты пропускаются;
   - back face: площадь по экранным координатам (loc1.xy) * `float(c16[0].x)` <= 0, гейт `c16[0].x != 0`;
   - small triangle: `floor(min+0.5) == floor(max+0.5)` по x или y (ни один центр пикселя не покрыт), гейт `c16[0].w != 0`;
   - occlusion (только bbox <= 8x8 px): 4x4 выборки Hi-Z `gp_t_tcb_8` (uv = px/1280, px/720, Lod 0), max по выборкам;
     треугольник отбрасывается если `min(z/w) - 6e-8 > max(HiZ)` — единственный `OpFOrdGreaterThan` в модуле.
3. **Треугольник эмитится всегда** (во всех ветках) — это depth pre-pass. Куллинг влияет только на компактный
   16-битный индекс-буфер `gp_s1`, который рисуют следующие проходы: видимые треугольники дописываются туда.
   Поэтому неверный cull = дыра в G-буфере при силуэте, который есть в pre-pass depth (ровно наблюдаемая картина).

Компактизация — Maxwell warp-идиома (SPIR-V `%63` = SHFL.UP с проверкой диапазона, `%61` = вставка 16-битного индекса через
`OpAtomicCompareExchange`):
```
b    = subgroupBallot(vis==1).x            // только слово 0 = 32 дорожки
if (b == 0) return                         // в варпе никто не видим
x    = vis*3
v    = shfl_up(x, 1)                       // эксклюзивный сдвиг
if (lane == 0) v = atomicAdd(gp_s0[0], bitCount(b)*3)   // база на весь варп
v   += shfl_up(v, 1/2/4/8/16)  (если lane-d >= 0)        // 5 шагов: покрывает ровно 32 дорожки
if (vis) write 3 indices at v
```

## Почему дыры
**Turnip (45-55%)**: лог `NVN caps subgroup size=128 stages=0x3f` — драйвер умеет subgroup-операции в GS, поэтому lone-lane
не применялся, и шейдер выполнялся на нативной волне 64/128. Идиома предполагает варп ровно 32:
- `ballot.x` считает только дорожки 0..31 -> для дорожек 32+ слоты в счётчике не резервируются;
- prefix-sum из 5 шагов складывает окно в 32 дорожки -> смещения дорожек 32+ попадают в чужие слоты / за счётчик.
В волне 64 теряется примерно половина видимых треугольников — совпадает с 45-55%. `warp_rewrite` (32-в-широких) работает
только для compute (stage 5) и на Adreno 750 выключен.

**Qualcomm (3-5%)**: `stages=0x30` (только FS+CS) -> GS уже переписан lone-lane (`rewrites=4`; проверено diff'ом
`work/703f1fcc3cda7204.out`): lane=0, ballot = свой бит, shuffle = своё значение. Тогда каждая инвокация сама делает
`atomicAdd(vis*3)` и пишет в `base` — **это корректно** (вывод в ACTIVE-PORT «lone-lane тут неверен» не подтверждается:
SHFL.UP с проверкой `lane-d >= 0` под lone-lane всегда берёт своё значение и не прибавляет, смещение = своя база).
Значит остаток на Qualcomm — не эмуляция дорожек, а один из тестов (кандидат №1 — Hi-Z occlusion / small-triangle:
тесты small-triangle и occlusion работают только для треугольников <= 8 px, т.е. плотные модели) либо потребление компактного
буфера (барьер GS-запись -> index/indirect чтение) либо прежняя проблема EQUAL-depth (с выключенными cvar'ами дыры
«почти» исчезают — часть остатка может быть не от куллинга). Статически это не различить — для этого сделан бисект-маск.

## Изменение
`dm/gfx/vulkan/engine/xbg_game.cpp` (`gscull_rewrite`, `lone_rewrite`), `xbg_spirv_lone.cpp`
(`xbg_spirv_gscull_shape` / `xbg_spirv_gscull_relax`), новый `xbg_spirv_gscull.h`.
`DM_GFX_GSCULL_FIX` — битовая маска (принимает 0x..), по умолчанию **1**:
- `1` — любой GS с subgroup-операциями всегда переводится в lone-lane (как на Qualcomm), даже если драйвер поддерживает
  subgroup в GS. Лечит Turnip. На Qualcomm ничего не меняет.
- `2` — выключить Hi-Z occlusion (единственный `OpFOrdGreaterThan` -> false);
- `4` — выключить small-triangle (гейт `c16.w != 0` -> false);
- `8` — выключить back face (гейт `c16.x != 0` -> false);
- `16` — выключить frustum (гейт `c16.z != 0` -> false);
- `30`/`31` — компактизация остаётся, но сохраняет все треугольники (диагностика: отделяет «тест режет» от «буфер теряет»).
Замена in-place на `OpLogicalAnd %bool %false %false` (те же 5 слов). Каждый бит применяется, только если найден ровно
один сайт; на всех шести шейдерах найдено ровно по одному (проверено Python-зеркалом правил, `spirv-val` OK, diff = 4 инструкции).
Лог: `NVN GS culling shader=... tests off mask=.. applied=..` и `NVN lone-lane ... forced (geometry warp idiom, DM_GFX_GSCULL_FIX)`.
Сборка: `cmake --build work/build-android --target dm` — OK.

## Как тестировать (с `DM_DOOM_GEOMCULL=1`)
1. Turnip: `DM_GFX_GSCULL_FIX=0` vs `1`. Ожидание: 45-55% дыр -> уровень Qualcomm. В логе для 6 ключей `lone-lane ... forced (geometry warp idiom`.
2. Qualcomm, бисект остатка: `1` (база) -> `31` (всё выключено). Если при `31` дыры остались — виновата не логика тестов, а
   потребление компактного буфера (барьеры/индексы) или EQUAL-depth; если ушли — `3`, `5`, `9`, `17` по одному тесту.
3. Сравнить fps `GEOMCULL=1 FIX=1` против `GEOMCULL=0`: куллинг должен оставаться выигрышем; при FIX=31 выигрыша нет
   (только стоимость GS).

## Риски
- lone-lane = один `atomicAdd` на видимый треугольник вместо одного на варп: больше атомарных операций на счётчик
  (на Qualcomm это уже так). Если GS-prepass на Turnip станет заметно дороже — следующий шаг: переписать идиому на
  нативный `subgroupBallot` (все 4 слова) + `subgroupExclusiveAdd` для GS там, где stage поддержан.
- Цикл `%61` перечитывает слово обычным `OpLoad` (не результатом CAS); корректно, но при некогерентном L1 может крутиться
  дольше. Не меняли.
- Биты 2..16 — только диагностика/обход: выключенный тест = больше треугольников в основном проходе (дороже, но без дыр).
- Бит 1 применяется ко всем GS со subgroup-операциями (в DOOM это только эти 6). VS/TES на Turnip с warp-идиомами
  (stages 0x3f) этим не покрыты.

## Раунд 2 (после теста на устройстве: дыры остаются и с выключенными тестами 3/5/9)
Тесты не виноваты — виновата передача компактного списка. Что проверено в `xbg_game.cpp`:
- **GPU-indirect путь** (`gpu_indirect_try`, ~245 draw/кадр, fallbacks=0, `xview`=0 в логах `work/logs/play/b_*`): args (20 Б,
  `indexCount` = счётчик `atomicAdd` в GS) и индексы берутся как `pending_view` того же слота; ленивый барьер
  (`storage_unbarriered`/`storage_dirty`) даёт `end_open_pass + full_barrier` (ALL_COMMANDS, MEMORY_WRITE -> READ, покрывает
  INDEX_READ и INDIRECT_COMMAND_READ). Индекс-адрес draw = начало диапазона GS (лог XVIEW: addr == writeback addr). Нарушений не нашла.
- storage chain / prologue copy / gpu merge в этих прогонах = 0; снимков индексов из guest-памяти (stale) нет.
- frontFace (TAA fix) на тест back face не влияет: знак считается в шейдере из экранных координат игры (loc1.xy) и `c16.x`,
  без участия Vulkan viewport/frontFace.

**Найденная ошибка (бит 32):** диапазон индексов объекта = `3*T*2` байт. Для нечётного числа треугольников T он кончается
посреди 32-битного слова (в capture: 39966, 44856... байт; соседние диапазоны начинаются с адреса ≡ 2 mod 4). GS пишет 16-битный
индекс через 32-битный `OpAtomicCompareExchange` (`%61`), и слово последнего индекса на 2 байта выходит за range дескриптора.
Устройство создаётся со всеми поддерживаемыми фичами (`vulkan_present.cpp`), т.е. с `robustBufferAccess` -> этот атомик
отбрасывается. Последний индекс используется только когда видны **все** треугольники объекта -> объект теряет последний
треугольник (старый индекс -> треугольник не проходит EQUAL-тест глубины -> дыра). Отсюда «чем больше треугольников
выживает, тем больше дыр»; при `=31` (все тесты выкл) это бьёт по каждому объекту с нечётным T. На Switch глобальная память
без robustness, запись проходит. Исправление: written storage-диапазоны выделяются с запасом до целого слова, range
дескриптора записываемой привязки округляется вверх до 4; writeback копирует только guest-диапазон (соседний объект не трогается).
Chain-переиспользование для невыровненных диапазонов выключено (его буфер мог быть без запаса).

**Бит 64 (латентный баг упорядочивания):** `OP_COPY_B2B` (CPU-путь) и `OP_UPDATE_UB` писали guest-память, не разрешая
pending GPU-результат на том же диапазоне: позже читатели брали старый GPU-результат, а writeback при retire затирал новые
данные (если игра так сбрасывает args/счётчики). Теперь перед записью `cpu_access(dst)` (sync только при пересечении).

`DM_GFX_GSCULL_FIX` по умолчанию теперь `0x61` (1|32|64). Сборка `cmake --build work/build-android --target dm` OK.

### Что запускать (все с `DM_DOOM_GEOMCULL=1`)
1. `DM_GFX_GSCULL_FIX=0x61` (дефолт) — ожидание: дыр нет / как без куллинга.
2. `DM_GFX_GSCULL_FIX=0x41` (без бита 32) — дыры должны вернуться, если причина в нём; `=0x21` (без 64) — проверка, нужен ли 64.
3. `DM_GFX_GSCULL_FIX=0x7f` (все тесты выкл + фиксы) — дыр быть не должно; против `=0x1f` (тесты выкл, без фиксов).
4. Если дыры всё ещё есть при `0x61`: `DM_GFX_GPU_INDIRECT=0` (CPU-путь с полной синхронизацией) и отдельно
   `DM_GFX_LAZY_STORAGE=0` (полный барьер после каждого draw с записью storage) — сузит до индиректа/барьеров.
5. Turnip: `DM_GFX_GSCULL_FIX=0x61` (бит 1 нужен там обязательно).
Не проверено на устройстве; гипотеза бита 32 опирается на код и размеры диапазонов из `work/capture.txt`, а не на трассу.

## Раунд 3 (0x61: дыр меньше, но есть; изредка огромный чёрный треугольник)
Ответы на вопросы координатора (по коду):
- **Откуда count.** `indexCount` = слово 0 аргументов DrawElementsIndirect (20 Б на объект, `gp_s0`), GS делает на нём
  `atomicAdd`. Следующий draw берёт args, а при count-варианте и count, через `gpu_indirect_try` → `pending_view`, т.е.
  GPU-буфер этого же слота после `full_barrier`. CPU не читает (в логах cpu=0, fallbacks=0, xview=0). Сброс счётчика делает
  игра: в нашем трансляторе — CPU-копией guest-памяти при записи GS-draw (`cpu_access` → `readback_buffer`). Если игра сбрасывает
  через ClearBuffer — он выполняется на CPU при записи и сначала разрешает pending (корректно). Через CopyBufferToBuffer /
  UpdateUniformBuffer раньше было некорректно, сейчас это закрыто битом 64.
- **Сдвиг базы / общее слово соседей.** Округление меняет только `range` дескриптора (`n`), `offset` прежний. Общего слова на
  GPU нет: каждый GS-draw получает свою копию своего диапазона (отдельная аллокация `readback_buffer`), запас в хвосте обнулён,
  writeback копирует ровно `bytes` гостевого диапазона. CAS по слову, где сосед начинается с адреса ≡ 2 mod 4, видит в хвосте
  нули, а не индексы соседа, и пишет обратно только свою половину → соседа не затирает.
- **robustBufferAccess и OOB-атомик.** По спеке OOB-атомик либо отбрасывается, либо пишет куда-то **внутри** диапазона, и его
  результат неопределён. Если Adreno зажимает адрес (clamp), до бита 32 последний индекс писался поверх другого индекса того же
  объекта → треугольник с вершинами из разных мест меша (большие треугольники). С битом 32 OOB больше нет.
- **Большой чёрный треугольник.** Разумные источники: (а) count > записанного (чтение индексов за диапазоном: индекс-буфер
  привязан к большой арене без размера, OOB-чтения индексов дают мусор из соседних аллокаций); (б) не связано с GS:
  GPU-частицы `cec755c4e27678b5` принудительно в lone-lane (ballot + shuffle в compute, компилятор Adreno падал), там «каждая
  инвокация — дорожка 0» может удваивать счётчики. Проверка: вспышки есть при `DM_DOOM_GEOMCULL=0`? Если да — это частицы, не GS.

**Новое: диагностический бит 0x100** (только с `DM_GFX_GPU_INDIRECT=0`, чтобы args читались на CPU после GPU). GS-диапазоны
запоминаются, и каждое indexed indirect draw, чьи индексы начинаются внутри такого диапазона, проверяется:
`firstIndex+count` за концом диапазона, count не кратен 3, старт не в начале → лог `NVN GS-cull args ... over=...`, раз в
5000 — `NVN GS-cull args ok checked=.. bad=..`.

### Env для прогонов (все с `DM_DOOM_GEOMCULL=1`)
1. `DM_GFX_GSCULL_FIX=0x161 DM_GFX_GPU_INDIRECT=0` — дыры/вспышки остались? в логе `grep "GS-cull args"`; bad>0 → count/диапазон
   неверны (прислать строки); bad=0 и дыры есть → индексы/count верны, виноваты тесты (п.2).
2. Бисект тестов с фиксами: `0x63` (без occlusion), `0x65` (без small), `0x69` (без back face), `0x71` (без frustum), `0x7f` (всё выкл).
   Прежние 3/5/9 были без бита 32 и недействительны.
3. Вспышки: тот же сценарий с `DM_DOOM_GEOMCULL=0` — если треугольник есть и там, он не от GS-куллинга.
4. Turnip: `0x61` и `0x161 DM_GFX_GPU_INDIRECT=0`.

## Раунд 4 (0x41 ≈ 0x61: бит 32 не главный; дыры есть и при 0x1f)
Новые диагностические биты `DM_GFX_GSCULL_FIX` (код в `gscull_rewrite` / `descriptors_build` / `execute_indirect`):
- **0x200 — identity compaction.** В GS результат `atomicAdd` (= слот в lone-lane, т.к. префикс-сумма ничего не прибавляет)
  заменяется на `3 * PrimitiveId` (добавлен вход BuiltIn PrimitiveId, `xbg_spirv_gscull_identity`). Счётчик по-прежнему
  увеличивается. Со всеми выключенными тестами (`0x27f`) компактный список = входной список в исходном порядке, count = 3T.
  SPIR-V проверен Python-копией правки + `spirv-val` на 703f1fcc.
  Дыры остаются → неверно читает потребитель (диапазон/смещение/count/снимок); исчезают → неверно назначение слотов/счётчик.
- **0x100 — проверка стартового count.** Перед GS-draw (CPU-путь, единственный в логах: chain/merge/prologue = 0) читается слово 0
  20-байтных аргументов из guest-памяти. Игра должна обнулять его каждый кадр. Ненулевой старт → лог
  `NVN GS-cull args start count=...` (иначе изредка `... start ok`). Это проверка гипотезы: если сброс игрой теряется (например,
  поздний writeback прошлого кадра поверх CPU-сброса игры), GS дописывает за конец диапазона (атомики теряются → дыры), а draw
  с count > ёмкости читает индексы за диапазоном (индекс-буфер привязан к арене без размера) → огромные мусорные треугольники.
  Это объясняет обе картины и «чем больше выживает, тем хуже». С `DM_GFX_GPU_INDIRECT=0` 0x100 ещё и проверяет args у draw
  (`NVN GS-cull args idx=... over=...`).
- **0x400 — принудительный старт count = 0** в копии аргументов для culling-GS (обход, если 0x100 покажет stale).

### Env для прогонов (все с `DM_DOOM_GEOMCULL=1`)
A. `DM_GFX_GSCULL_FIX=0x161 DM_GFX_GPU_INDIRECT=0` → `grep "GS-cull args"`: строки `start count=` (stale) и/или `over=`.
B. `DM_GFX_GSCULL_FIX=0x461` — если A показал stale: дыры и вспышки должны уйти.
C. `DM_GFX_GSCULL_FIX=0x27f` (identity, тесты выкл) против `0x7f` (тесты выкл, атомарные слоты).
D. Turnip: те же A/B.

## Раунд 5: зависание прогона A
`DM_GFX_GPU_INDIRECT=0` + 0x100 повис (`SyncWait` крутится). Проверка 0x100 на CPU-пути только читает память (`memcpy`),
блокирующего в ней нет; зависание, скорее всего, даёт сам CPU-путь indirect (`cpu_access` → `resolve_pending` → полный sync на
каждый indirect-draw при асинхронной трансляции). **`DM_GFX_GPU_INDIRECT=0` больше не использовать.**
0x100 теперь работает на GPU-пути без блокировок: для каждого 8-го indexed indirect draw из GS-диапазона аргументы (и count,
если есть) копируются `vkCmdCopyBuffer` в host-буфер слота сразу после draw, проверка — в `Retire`-хендлере, когда фенс слота
уже просигналил. Лог тот же: `NVN GS-cull args idx=... over=... gpu` / `... ok checked=... gpu`. Стоимость — разрыв прохода на
каждую выборку (только диагностика). Стартовый count (`args start`) проверяется как раньше (запись команды, без ожидания).

Прогон A': `DM_DOOM_GEOMCULL=1 DM_GFX_GSCULL_FIX=0x161` (без `DM_GFX_GPU_INDIRECT`) → `grep "GS-cull args"`.

## Раунд 6 (B 0x461 и C 0x27f: дыры остаются → неверны ЗНАЧЕНИЯ индексов или чтение)
**Выравнивание дескрипторов (вопрос координатора) — не причина.** Каждый записываемый storage-диапазон GS получает свою
аллокацию `readback_buffer` с выравниванием арены `max(256, minStorageBufferOffsetAlignment, …)`. Привязка: offset = начало
аллокации, `buffer_offset` = 0 (args и индексы не сливаются). Базу вниз никто не выравнивает. Транслированный GS адресует
относительно начала привязки (`p0>>2`, `(p0&3)*8`), и потребитель читает тот же буфер с того же начала (`pending_tail`,
offset кратен 4, `UINT16`). Пол-слова не переворачиваются. GS не читает входной индекс-буфер (индексы приходят из VS через
varying), его привязка у prepass-draw та же, что без куллинга.

**Новая гипотеза — значения.** Все 6 пар VS→GS (VS `53014b…`, `fc05bdb8…`, `58c04902…`, `965e2c6a…`, `e2ce6d30…`, `badf12d9…`)
передают индекс как **биты float**: в VS `intBitsToFloat(gl_VertexIndex)` → float-temp → `floatBitsToInt` → `& 0xffff` →
`intBitsToFloat` → varying; в GS varying → float-temp → `floatBitsToInt` → 16-битная вставка. Любой индекс 1..65535 в таком
виде — денормал fp32. Если компилятор где-то копирует его float-move'ом с flush-to-zero, индекс становится 0. Треугольник
тянется к вершине 0 меша: огромный чёрный треугольник, а на месте настоящего — дыра. Срабатывает частично, в зависимости от
того, как компилятор разложил копии; виден только в компактном списке (без куллинга эти значения никто не читает). Это
согласуется с B и C: слоты и счётчик правильные, значения нет. Подтверждения на устройстве нет.

**Исправление (бит 0x800, по умолчанию выкл, для A/B):** `xbg_spirv_index_carrier` переводит перенос индекса со «значения в
битах» на «значение»: в VS каждый `OpBitcast` на пути VertexIndex→выход становится `ConvertSToF`/`ConvertFToS`; в GS — три
`OpBitcast float→int`, чьи результаты идут во вставку индекса (функция с CAS). Точно до 2^24, на месте (та же длина
инструкций). Проверено Python-копией правила: все 6 VS и 4 GS в бандле дают по 3 замены, `spirv-val` OK. VS-правило
(VertexIndex → `& 0xffff` → выход) совпадает ещё с 16 VS бандла, не встреченными в дампах. Если какой-то из них работает
без GS и FS читает этот varying как биты, такой draw сломается. Поэтому бит выключен по умолчанию. В логе:
`NVN index carrier shader=… stage=0/3 conversions=3`.

## Раунд 7 (0x861: carrier ПРИМЕНИЛСЯ, дыры остались → гипотеза денормалов на пути VS→GS снята)
**Почему «не было строки»** — была. `work/logs/play/g_carrier/logcat.txt`, строки 4231-5331: `NVN index carrier ... loader=warm
stage=0 conversions=3` для всех 6 VS пары и `stage=3 conversions=3` для всех 6 GS (+ lone-lane `forced`). Путь: warm-лист
(`warm list=261`, `shader loads take the warm-up's rewritten SPIR-V=1`, `PERF pipelines warm_built=261 created=0`) — все
пайплайны собраны из переписанного SPIR-V; Vulkan pipeline cache ключуется драйвером по содержимому модуля и переписку не
обходит. Строки `NVN GS culling shader=` не было потому, что при маске без битов 2..16/0x200 функция выходила до лога —
теперь логирует всегда (`... mask=%#x (no test / identity bits)`).
Замечание: VS-правило carrier сработало ещё на ~12 VS вне пар (`c86fd0cb…`, `3db76a7a…`, `bbe78cd1…` conversions=4 и др.) —
0x800 оставлять выключенным.
Float controls: устройство не трогаем (SPV_KHR_float_controls / DenormPreserve не нужны) — 0x861 показал, что перенос
значения индекса не причина.

**Новое: бит 0x1000** (`xbg_spirv_cas_int_temps`, `xbg_spirv_lone.cpp`). Последнее место, где биты индексов идут через float:
эмуляция 16-битной записи (`%61`, CAS-цикл) держит СТАРОЕ 32-битное слово (два индекса) во float-временной
(`load uint → bitcast float → store`, потом `load float → bitcast uint` для BFI и компаратора CAS). Верхний индекс < 128 —
денормал, 0x7f80+ — NaN. Переписка делает эту переменную uint (OpVariable/OpLoad меняют тип, bitcast'ы → OpCopyObject), на месте,
только если все ссылки распознаны. Python-зеркало: 703f1fcc/351c0bfc (.out, lone-lane) и 703f1fcc/78c87a04 (.spv, исходные) —
по 1 переменной, `spirv-val` OK, diff = 7 инструкций. Лог: `NVN GS-cull CAS int temps shader=... retyped=1`. Честно: если бы
драйвер портил это слово, вероятнее был бы вечный цикл CAS (зависание, ср. раунд 5), чем дыра — бит закрывает вариант, не более.

**Что ещё может давать дыры при identity compaction (0x27f), раз значения и слоты верны:**
1. **Повторное исполнение GS на тайлере (главный кандидат).** Adreno рендерит по бинам; спецификация разрешает исполнять
   шейдеры вершинного конвейера больше одного раза (side effects при `vertexPipelineStoresAndAtomics` не гарантированы
   «ровно один раз»). Если GS с атомиками гоняется в binning-проходе и/или в каждом бине, `count` = k·3T: в обычном режиме
   поздние дописывания уходят за диапазон (отбрасываются) → дыры там, где бин обработан позже; потребитель с count > ёмкости
   читает индексы за диапазоном → огромные треугольники. В identity-режиме слоты одинаковые, но count всё равно завышен.
   Проверка — 0x100 на GPU-пути (прогон A' раунда 5 так и не был сделан): строки `GS-cull args ... over=` с over>0 и
   count > 3·T. Если подтвердится — лечение: вынести culling-GS в отдельный проход без привязанного цвета/с малым рендер-ареа
   или пересчитать count на GPU (min(count, cap)) перед indirect-draw.
2. **Ленивые барьеры** (`storage_dirty` диапазонный): GS-запись → INDEX_READ/INDIRECT_READ. `DM_GFX_LAZY_STORAGE=0` ни разу
   не прогонялся с куллингом.
3. **Позиции prepass (VS+GS) vs шейдинг (VS)** для EQUAL-теста: если игра при `GEOMCULL=0` рисует prepass без GS, то дыры
   могут быть разницей позиций, а не индексов. `DM_GFX_INVARIANT=1` пробовали без куллинга; с куллингом — нет.
