Без телефона и запусков: код (`xbg_game.cpp`, `hle_nvn.c`, `nvn_dirty.c`) + логи `work/logs/play/fl_chunk|fl_nochunk|fl_vtbase`
(в них нет `DM_GFX_VT_DIAG`, `DM_NVN_COUNT`, скриншотов — по ним причину не выделить, только исключить).

## 1. Что исключено / что найдено

| # | Гипотеза | Вывод |
|---|---|---|
| — | VT_FIX / chunked submit | Исключены владельцем (мерцает во всех трёх прогонах). В логах ничего особого: partial-tex 1-5 загрузок/кадр, длинные кадры — GPU-bound бой, не совпадают с «миганием». |
| 2a | GPU читает слот кэша, пока его перезаливают | **Нет.** `partial_upload` пишет `vkCmdCopyBufferToImage` в *текущий* записываемый слот (`Commands` = тот же `s.cmd`, `full_barrier` ALL_COMMANDS до/после, `transition` с MEMORY_READ/WRITE). Команды прошлых кадров уже раньше в потоке → они дочитают старое; данные — снимок в staging. Порядок GPU корректен при любом числе кадров в полёте. |
| 2b | **Гонка CPU: WriteTexels (поток транскода) ↔ наша проверка + partial_upload (поток трансляции)** | **Реальная дыра в коде.** `write_texels` делает `dm_guest_write_prepare` (снять защиту, `gen=++now`) и *потом* долгий memcpy по 16 байт. Трансляция параллельно: `nvn_dirty_protect` → `stamp=now` → читает блок. (а) Если чтение попало в середину memcpy — на GPU уходит наполовину новая страница; дозапись падает в fault → `gen>stamp` → чинится в **следующем** guest-submit (≈1 кадр рваной страницы = вспышка). (б) Если страница в момент protect была `BUSY` (писатель как раз снимал защиту), protect её пропускает: страница остаётся writable с `gen<=stamp`, остаток memcpy не даёт fault и **никогда** не перезаливается, пока слот не перепишут. Окно маленькое, но WriteTexels 1k–130k вызовов / 10 с. |
| 1 | Переподписка кэша (≈1024 слота vs 2.8-4.4k различных значений feedback) | Возможна, по логам не доказать (distinct ≠ страницы). Симптом трэша — слот переписывается каждые несколько кадров, мипы «прыгают» → мерцание. Добавлен прямой счётчик (ниже). |
| 3 | Шейдер земли / quad-рерайт производных | Производные решают и мип VT, и выбор LOD у слоёв terrain. `DM_GFX_QUAD_DERIVATIVES=1` (ставит приложение) — кандидат на A/B. |
| 3' | **GS-куллинг с Hi-Z** (`prezdrawmotionvector*`, lone-lane) | Сильный кандидат: треугольники земли, отброшенные Hi-Z по прошлому кадру, пропадают на кадр = «мигание». Бит 2 `DM_GFX_GSCULL_FIX` выключает Hi-Z-тест, 30 — все тесты. |
| 4 | TAA на статике | После `DM_GFX_TAA_FIX=2` вектора камеры правильные; проверять `r_antialiasing 0`. |

## 2. Что добавлено в код (всё компилируется: `cmake --build work/build-android --target dm`)

1. **`DM_GFX_VT_ATOMIC=1`** (по умолчанию 0 = прежний lock-free путь, байт-в-байт).
   - `nvn_dirty.c/.h`: `nvn_texel_sync_on()` (читает env один раз, пишет `[nvn] DM_GFX_VT_ATOMIC=N` в лог), `nvn_texel_lock/unlock` (один mutex).
   - `hle_nvn.c`: `nvnTextureWriteTexels(Strided)` держит lock на весь `write_texels` (unprotect + memcpy).
   - `xbg_game.cpp` `get_image_slow`, ветка tracked: RAII-guard держит lock на protect + stamp + `partial_upload`/hash.
   - Итог: снимок страницы либо целиком до записи, либо запись целиком после (с `gen>stamp`) — нет рваных страниц и нет потерянной записи (2b-а и 2b-б). Цена: WriteTexels ждёт partial_upload (обычно <1 мс), только при контенции.
2. **Диагностика в `DM_GFX_VT_DIAG=1`** (строка `NVN VT feedback ...`, раз в 300 write-back'ов) — новые поля:
   - `torn=N` — перезалитые GOB-блоки, чьи страницы CPU переписал *после* нашего protect (во время/сразу после чтения; верхняя оценка). При `VT_ATOMIC=0` >0 → гонка 2b реальна; при `VT_ATOMIC=1` должно быть ≈0.
   - `reup<16=N reup<128=M of K blocks` — сколько перезаливок блока того же адреса (≈ того же физ. слота кэша/таблицы) случилось через <16 / <128 guest-submit'ов (~2 / ~16 кадров при ~8 submit/кадр) после прошлой. Высокая доля `reup<16` → кэш трэшит (гипотеза 1); таблица 98 закономерно перезаливается часто — смотреть вместе с `partial(98:..., 103:...)`.

## 3. A/B на устройстве (Мi 14 Ultra, Марс, пустыня; одна точка, стоять/медленно поворачивать 60 с, видео или скриншоты)

Всегда: `DM_GFX_VT_DIAG=1 DM_GFX_PERF_SAMPLE=4`. Каждый прогон — оценка «мерцает: да/реже/нет». Игровые cvar'ы — через `DM_DOOM_ARGS="+set ..."`.

| # | env / cvars | Если мерцание пропало → |
|---|---|---|
| A | база (только диаг) | эталон: записать `torn`, `reup<16`, `partial 103/98` |
| B | `DM_GFX_VT_ATOMIC=1` | **гонка 2b** — оставить, сделать дефолтом. `torn` должен упасть до ≈0 |
| C | `DM_GFX_GSCULL_FIX=0x63` (Hi-Z-тест GS выкл.) | Hi-Z-куллинг (3'); затем `0x7f` (все тесты выкл.) для подтверждения |
| D | `DM_GFX_QUAD_DERIVATIVES=0` | quad-рерайт производных (3) |
| E | `+set vt_feedbackLodBias 1` | трэш кэша (1): страниц меньше; ещё `+set vt_feedbackHighWater 100 +set vt_feedbackLowWater 99` |
| F | `+set vt_maxPPF 8` (и `128`) | 8 лучше → мерцание от частой смены страниц; 128 лучше → недогрузка |
| G | `+set r_skipDecals 1` | z-fighting декалей (5) |
| H | `+set r_skipFoliage 1` | трава/кусты пустыни, не земля |
| I | `+set r_antialiasing 0` | TAA (4) |
| J | `DM_GFX_PARTIAL_TEX=0` | контроль upload-стороны в целом (медленно: полные хэши/перезаливки) |
| K | `+set vt_showPageMips 1` (или `vt_showPageColors 1`) | визуально: мигает ли раскраска мипа на земле (трэш) или цвет стабилен (не VT) |

Порядок: A → B → C → E → D → G/I → остальное. Если B помогает частично — B+C, B+E.

Интерпретация `NVN VT feedback`: `torn>0` в A и мерцание ушло в B — причина 2b. `reup<16` порядка сотен на окно у 103
и E лечит — переподписка (лечение: дефолтный `vt_feedbackLodBias`/HighWater через `DM_DOOM_ARGS`, либо искать почему
feedback просит больше страниц, чем на Switch: производные/масштаб UV). Ничто из VT не влияет, а C лечит — Hi-Z GS-куллинг
(сверить Hi-Z-текстуру/строки после TAA_FIX=2 и порог глубины).
