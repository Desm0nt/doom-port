# DOOM: тени «выскакивают» на один кадр — разбор и A/B-план (2026-10-28)

Без телефона и запусков: видео `work/logs/flicker/flicker.mp4`, `rec2.mp4`, GLSL игры (`tools/doom_shader_jobs.py`),
`xbg_game.cpp`, `hle_nvn.c`, логи `work/logs/play/fk_*` (`sh_*` пустые).

## 1. Что видно на видео

* `flicker.mp4` (60 fps по HUD, ~0.1–0.8 с): кадр с чёткой «решёткой» на земле повторяется **периодически**: записанные
  кадры 13, 18, 23, 28, 33, 39, 44 (t = 0.186 … 0.671 с) — шаг ≈ 80 мс ≈ **5 игровых кадров**. В этот кадр пропадает и
  обычная тень скалы — меняется *вся* тень солнца, а не её кусок. Около 6.9–7.25 с то же с шагом ≈ 4 кадра (51 fps).
* `rec2.mp4` 7.4–8.2 с: у колонны вся сцена то в тени солнца (почти все кадры), то залита солнцем (единичные кадры), геометрия та
  же. Это не дыра геометрии и не прямоугольник scissor/clear — переключается результат теста тени солнца по всему экрану.
* Вывод: в отдельные кадры lit-шейдер берёт для солнца не те данные (матрица каскада / прямоугольник атласа / содержимое
  тайла), что в соседних кадрах. Локальная порча атласа (неверный clear, сдвиг scissor) так не выглядит.

## 2. Как DOOM читает тень солнца (`outside_nx`, все lit-шейдеры)

* Списки света по кластерам (SSBO `clusterlightsid`), параметры источника — UBO `lightparms1..3[1024]`, параметры тени —
  UBO `shadowsparmsubo[819]` (80 Б × 819 ≈ 64 КБ), индекс `light_parms >> 22`. Для параллельного источника выбирается каскад
  0/1/2 (+ дизер `parallellightslicescale`), затем `shadowTC.xy * shadowAtlasScaleBias.xy + .zw` и PCF по
  `samp_shadowatlasdepthcomparemap`.
* Таблицы пересобирает CPU каждый кадр. Порядок источников и тайлы атласа между кадрами разные. Если кадр прочитает таблицу
  *другого* кадра, у солнца окажутся чужие матрица и тайл. Получится ровно то, что на видео: глобальный флип тени или чужая
  чёткая тень.
* Запись атласа: `shadowclear` — полноэкранный треугольник с `gl_FragDepth = 1` внутри viewport/scissor тайла.
  `rendertexcopy2ddepth` — `texelFetch(src, gl_FragCoord.xy + texcopysrcoffset)` (статический кэш → атлас,
  `r_shadowRenderDepthCopy`). Дальше depth-only `shadowvmtr*` (mvp из UBO).

Scissor (`xbg_clear_rectangle`) не флипается ни в одном режиме — согласовано: при LOWER_LEFT строка окна = строка памяти. ## 4. Главный кандидат: zero-copy UBO читается GPU позже, чем ждёт игра

* `DM_GFX_ZEROCOPY` (дефолт DOOM = 1): uniform-блок привязывается прямо к guest-памяти (`zc::view`), GPU читает его в момент
  исполнения. А это до кадра после guest-submit: Vulkan-сабмит один на кадр при present (или кусок chunk), плюс слот в полёте.
  Снапшот (без zc) копирует блок в момент трансляции, то есть ровно при guest-submit, как на Switch.
* Если игра пишет таблицы следующего кадра в память, которую наш GPU ещё не прочитал, то кадр N освещается таблицами N+1.
  Это возможно, если её кольцо кадров рассчитано на синхронизацию Switch, а наша её ослабляет:
  * acquire-sync fenced на прошлый present этой текстуры (`[DOOM]`, nx2android 1c6177d, откат — `DM_NVN_ACQ_NOW=1`);
  * отложенные события (`DM_GFX_DEFER_EVENTS=2`);
  * present / chunk-разрезы.
  Периодичность (≈ каждые 4–5 кадров) похожа на «биение» CPU и GPU, когда GPU-bound кадр иногда даёт CPU уйти дальше.
* Не доказано: в логах нет ни одной строки, которая это показала бы. Поэтому сделан детектор.

### Что добавлено (`xbg_game.cpp`, `namespace zcubo` перед `uniform_snapshot`; сборка `cmake --build work/build-android --target dm` — OK)

* **`DM_GFX_ZC_RACE=1`** — детектор. Zero-copy UBO ≥ 4 КБ (таблицы света, теней, декалей) хэшируются при привязке. На каждом
  следующем guest-submit блок перехэшируется, пока его Vulkan-сабмит ещё может быть не прочитан (слот пишется или висит с
  несигнальным fence). Изменение = CPU переписал блок, который GPU ещё прочтёт. Лог:
  * `NVN zc-ubo race: block ADDR+BYTES ... still recording|in flight (frame N)` — первые 24 случая;
  * `NVN zc-ubo frames=300 bypassed= tracked= checks= changed= changed_KB=` — раз в 300 present.
  Цена: ~10 мкс на 64 КБ на проверку, только при включённом env.
* **`DM_GFX_ZC_UBO_MIN=N`** (по умолчанию 0 — поведение байт-в-байт прежнее) — кандидат на исправление. Uniform-блоки ≥ N байт
  идут не через zero-copy, а через снапшот на момент guest-submit. `4096` — только таблицы, `1` — все UBO. Стоимость:
  копия ~0.3–0.5 МБ на кадр (дедупликация по адресу в пределах submit), заметно дешевле `DM_GFX_ZEROCOPY=0`.

G/H сузят, какой проход.

## 6. Риски

* `ZC_UBO_MIN` меняет только откуда берётся UBO (снапшот вместо прямой привязки) — это путь `DM_GFX_ZEROCOPY=0`, проверенный
  ранее. Если игра *намеренно* дописывает UBO после submit (маловероятно), снапшот покажет данные на момент submit, как Switch,
  который к тому времени уже начал исполнять.
* Детектор даёт ложные срабатывания, только если игра пишет в блок, привязанный в ещё не исполненном сабмите, — а это и есть
  искомая гонка.

## 2. Механизм (доказательства из `work/capture.txt`, `work/dump*/draws.txt`, GLSL игры)

* Атлас: serial 28, 4096x4096, NVN fmt 0x32 → `VK_FORMAT_D16_UNORM` (124). Все тайлы (кэши статики, каскады, споты)
  рисуются в **один** depth-only `VkRenderPass` (renderArea = весь атлас), смена viewport/scissor проход не рвёт.
* Порядок в кадре (capture, события 235414…235720): `shadowclear` + статические кастеры в тайлы-кэши 512² (2048,2048 /
  3072,2560 / 1536,3072), потом `rendertexcopy2ddepth` (ps `e5ce9e6261106dd7`:
  `gl_FragDepth = texelFetch(samp_texcopysrc2d, gl_FragCoord.xy + texcopysrcoffset)`) в динамические тайлы 2560,2560 /
  2048,3072 и т. д., затем динамические кастеры. В capture у копии `TEXTURE ... serial=28` и `FEEDBACK input=... serial=28` —
  **источник копии — тот же атлас, что и depth-attachment открытого прохода**. За кадр ~20 таких копий (512/256/128/64).
* У нас: guest-барьеры DOOM пропускаются (`OP_BARRIER`, `DM_GFX_GUEST_BARRIER` по умолчанию 0) — порядок обеспечивает
  `prepare_read`. Но в `prepare_read` есть shortcut depth-feedback (`DM_GFX_DEPTH_FEEDBACK`, по умолчанию 1): чтение
  depth-attachment открытого прохода без разрыва, если проход depth-only (`!color_targets`), даже когда он уже писал глубину
  («only farther than the truth» — верно для Hi-Z GS-куллинга своего же буфера, **неверно** для копии тайл→тайл).
* На тайлере (Adreno) запись глубины этого прохода лежит в GMEM/кэшах до конца прохода. Копия читает память: свежие бины
  кэша статики есть только там, где бин уже сохранён, — остальное старое (позиция каскада до сдвига) или clear.
  Кэш статики перерисовывается не каждый кадр: только когда каскад сдвигается за `r_shadowParallelMoveMargin` при движении
  камеры (≈ раз в 5–8 кадров на видео) → **ровно один плохой кадр**, в следующем кадре кэш уже в памяти, и копия верная.
  Это объясняет все наблюдения: одиночность, связь с движением, «решётку» (граница бинов), «солнце везде» (не сохранённый
  clear), отсутствие эффекта от ZEROCOPY/VT/chunk/throttle. Тёмные пятна у трупа (rec2 12.25–12.5 с) — тот же путь для
  тайлов 64/128 (споты/тени объектов копируются так же).
* Остальные гипотезы: (a) frontFace — в capture игра сама чередует `front` по тайлам (каскады/споты с отражённой проекцией),
  cull=2 только у кастеров, `shadowclear`/копия cull=0; bit 2 TAA_FIX инвертирует frontFace единообразно → смысл culling
  сохраняется. (c) вид атласа один (serial 28, view 124, D16 без stencil). (d) `NVN XVIEW` в fk_quad0 — только кадры
  2564–2570 (загрузка), в PERF `xview views=0.00`: не связано. (e) TAA не создаёт геометрии теней, решётка видна до TAA.

## 3. Исправление (`xbg_game.cpp`, `depth_feedback_mode()` / `prepare_read`; сборка `cmake --build work/build-android --target dm` — OK)

`DM_GFX_DEPTH_FEEDBACK` теперь трёхзначный:
* `1` — по умолчанию, поведение байт-в-байт прежнее;
* `2` — **фикс**: shortcut только пока открытый проход ещё не писал глубину; чтение своего depth-attachment после записи
  завершает проход + full barrier (обычный путь `read break`, why=4/6). Первые 16 случаев в логе:
  `NVN depth-feedback break (DM_GFX_DEPTH_FEEDBACK=2) serial=28 fmt=0x32 4096x4096 frame=N`; при значении ≠1 в лог пишется
  `NVN DM_GFX_DEPTH_FEEDBACK=N`;
* `0` — shortcut выключен совсем (старый ключ, работает **на текущем APK без сборки**).

Цена `2`: до ~20 разрывов прохода атласа за кадр (store + барьер + новый проход с LOAD). На Adreno может стоить 0.5–2 мс GPU —
измерить. Если дорого: следующий шаг — копию тайл→тайл делать вне прохода (`vkCmdCopyImage` региона по `texcopysrcoffset`,
он лежит в UBO c4 копии) или группировать копии после всех статических тайлов.

## 4. A/B на устройстве

Сцена: место из `flicker.mp4` (медленно вести камеру/идти 20 с) + бой у колонны из `rec2`. Запись экрана, покадровый
разбор: `ffmpeg -i x.mp4 -fps_mode passthrough` и разница соседних кадров (скрипт: средняя |Δ| по кадру, плохой кадр даёт
пик 14–21 при фоне 3–5). Всегда `DM_GFX_PERF_SAMPLE=4`, `DM_DOOM_ARGS="+set com_showFPS 1"`.

| # | env | Ожидание |
|---|---|---|
| A | база (`DM_GFX_DEPTH_FEEDBACK=1`) | мигание есть (эталон, fps) |
| B | `DM_GFX_DEPTH_FEEDBACK=0` (**без сборки**) | мигание пропало → причина подтверждена; fps ниже (рвутся и GS-проходы) |
| C | `DM_GFX_DEPTH_FEEDBACK=2` (новая сборка) | мигание пропало, в логе `depth-feedback break ... serial=28 4096x4096`; fps ≈ A (сравнить `NVN PERF ... gpu_ms`, `read_break .../attach`) |

заменить `:1` на `:2`). Если B/E **не** лечат — гипотеза неверна, вернуться к §5 раунда 1 (G/H/I).
